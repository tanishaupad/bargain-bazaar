# Bargain Bazaar

A playable multilingual bargaining game built with Next.js, TypeScript, Tailwind CSS, and the official `sarvamai` JavaScript SDK.

## Run locally

1. Install dependencies with `npm install`.
2. Copy `.env.example` to `.env.local` and add your Sarvam API key. Redis credentials are optional for local development.
3. Start the app with `npm run dev` and open [http://localhost:3000](http://localhost:3000).

Choose English, Hindi, Hinglish, Telugu, Tamil, or Bengali. Each new game picks from 10 products and randomizes the seller, asking price, hidden seller minimum, buyer value, and patience. You know your own value, which is the most you may offer; the seller does not. Enter a whole-rupee offer plus a message on each turn. A deterministic server-side engine decides whether the seller accepts, rejects, counters, or walks away. Seller styles change acceptance thresholds, lowball tolerance, and concession size. Games last at most six rounds. The final card reveals the transaction price, buyer payoff (`buyer value − price`), seller payoff (`price − seller minimum`), and the seller's minimum. A post-game strategy report scores the buyer's captured surplus and explains one concrete bargaining opportunity. A replay shows every offer, private acceptance threshold, counteroffer, patience change, and decision rule; both stay hidden during negotiation.

The **Shopkeeper Mode** tab reverses the roles. Pick any catalog item, see its purchase cost, select the customer languages you can bargain in, and set a listing price. The next customer's preferred language is randomly chosen only from that selection (English is the default). A randomized AI customer opens with an offer. You can accept, reject, counter with a message, or walk away. The customer's maximum willingness to pay, patience, and personality stay server-side during play. Afterward, the result reveals their maximum, your realized profit, and the share of available seller surplus you captured. Customer dialogue may hint at urgency, competitor comparisons, or a changing story. Deterministic TypeScript logic decides every offer and outcome; Sarvam only writes the customer's words. A missing or failed Sarvam call uses a short fallback reply. The seller can write in a different supported Indian language or script; Sarvam is prompted to understand it and answer mainly in the customer's chosen language.

The browser calls `POST /api/game` to start Customer Mode, `POST /api/game/turn` for each offer, and `GET /api/game?id=…` to restore a session after reload. Shopkeeper Mode uses the matching `/api/shopkeeper` and `/api/shopkeeper/turn` routes. Turn requests include the round the browser expects. The server atomically stores the engine's decision and a fallback reply before calling Sarvam's `sarvam-105b-conversations` model; Sarvam can update only the reply text. The engine owns the decision and price. The API key stays on the server and is never sent to the browser.

With `UPSTASH_REDIS_REST_URL` and `UPSTASH_REDIS_REST_TOKEN` configured, game sessions and chat transcripts are stored in Redis with a two-hour expiry. Updates use an atomic compare-and-set, so two requests cannot advance the same round. In local development without Redis, the ignored `.data/games` directory remains available. Production requires Redis credentials unless `ALLOW_LOCAL_STORE=true` is explicitly set for a single-machine deployment. The browser keeps only the random session ID. No login, voice, or payment flow is included. If Sarvam is unavailable, the engine still completes each turn with a short fallback reply.

## Deploy

Create an Upstash Redis database and set `UPSTASH_REDIS_REST_URL`, `UPSTASH_REDIS_REST_TOKEN`, and `SARVAM_API_KEY` as server-side environment variables on the Next.js host. Deploy the repository as a Next.js application. The API limits new games to 10 per hour per visitor and turns to 60 per hour per visitor plus a global cap of 300 turns per hour. On Vercel, visitor identity uses its trusted forwarded-IP header; on other hosts, the conservative anonymous limit applies until a trusted proxy identity is configured. A production deployment without Redis credentials fails instead of writing session state to ephemeral local disk.

Run `npm run lint`, `npm run test`, and `npm run build` to check the game. For browser tests, run `npx playwright install chromium` once, then `npm run test:e2e` after building. The Playwright server uses a separate port and local session store with no Sarvam key, so tests do not consume API credits. GitHub Actions runs all four checks on pushes and pull requests.
